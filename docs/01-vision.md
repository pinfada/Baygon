# Chapitre 1 — Vision

## Préambule

Baygon est né d'un constat simple.

Le développement logiciel moderne est devenu dépendant d'un poste de travail.

Un ordinateur portable devient progressivement le centre de la vie du développeur.

Il contient :

- les outils ;
- les clés SSH ;
- les secrets ;
- les environnements ;
- les scripts ;
- les accès ;
- les habitudes.

Cette dépendance crée de nombreuses contraintes :

- impossible de travailler confortablement depuis un téléphone ;
- impossible de reprendre rapidement son activité après une panne matérielle ;
- temps perdu à reconstruire un environnement ;
- multiplication des interfaces d'administration ;
- fragmentation des outils.

Baygon est la réponse à ce problème.

---

# Vision

Créer un système permettant à un développeur de retrouver instantanément son environnement de travail depuis n'importe quel appareil.

L'utilisateur ne dépend plus d'une machine.

Il dépend uniquement de son identité.

L'objectif est que tout appareil connecté à Internet puisse devenir un poste de travail.

---

# Mission

Construire une couche d'orchestration légère permettant de piloter un écosystème logiciel complet au travers d'une interface unique.

Cette couche doit masquer la complexité des différents fournisseurs sans chercher à les remplacer.

---

# Ce que Baygon est

Baygon est un orchestrateur.

Baygon est un moteur de contexte.

Baygon est un assistant d'ingénierie.

Baygon est une interface entre un utilisateur, son infrastructure et un modèle d'intelligence artificielle.

Baygon est un accélérateur de productivité.

---

# Ce que Baygon n'est pas

Baygon n'est pas un cloud.

Baygon n'est pas une plateforme PaaS.

Baygon n'est pas un IDE.

Baygon n'est pas un système de monitoring.

Baygon n'est pas une base de données.

Baygon n'est pas un fournisseur Git.

Baygon ne remplace aucun outil spécialisé.

---

# Objectifs

Les objectifs principaux sont :

- supprimer la dépendance au poste de travail ;
- centraliser les interactions avec l'écosystème ;
- permettre le travail depuis un téléphone, une tablette ou un ordinateur ;
- réduire le temps consacré à l'administration ;
- offrir une interface naturelle grâce à l'IA ;
- conserver une architecture extrêmement simple.

---

# Philosophie

Baygon privilégie toujours :

la simplicité avant la richesse fonctionnelle.

la composition avant la réécriture.

les standards ouverts avant les solutions propriétaires.

les services managés avant les composants auto-hébergés.

la configuration avant le développement.

l'orchestration avant l'implémentation.

---

# Devise

Une question.

Une réponse.

Depuis n'importe où.

---

# Les cinq principes fondateurs

## 1. Minimalisme

Chaque ligne de code possède un coût de maintenance.

Le meilleur code est celui qui n'a jamais eu besoin d'être écrit.

---

## 2. Interopérabilité

Chaque fournisseur doit pouvoir être remplacé.

Aucun composant ne doit enfermer Baygon.

---

## 3. Mobilité

Toutes les fonctionnalités essentielles doivent être accessibles depuis un téléphone.

L'ordinateur ne doit jamais être une obligation.

---

## 4. Intelligence

L'utilisateur ne doit pas connaître les commandes.

Il expose son intention.

Baygon décide des actions à entreprendre.

---

## 5. Pérennité

Baygon doit rester pertinent indépendamment :

- du fournisseur cloud ;
- du fournisseur Git ;
- du modèle d'IA ;
- du système d'exploitation.

---

# Définition du succès

Baygon sera considéré comme réussi si un développeur peut :

- perdre son ordinateur ;
- acheter un nouvel appareil ;
- reprendre son travail en moins de cinq minutes.

Sans reconfiguration.

Sans perte de données.

Sans dépendance au matériel.

---

# Première règle d'architecture

Baygon ne développera jamais une fonctionnalité déjà mieux réalisée par un outil existant.

Il préférera toujours orchestrer plutôt que remplacer.

Cette règle est absolue.
